Caching — Cache-Aside

Serve hot reads from Redis; fall back to the DB and backfill on a miss.

● Naive — miss never cached
GET /product/5
Query DB every time
~2000 ms, no backfill
Every request stays slow 🐢
● Cache-aside
GET /product/5
check Redis
HIT
return · ~2 ms ⚡
MISS → DB
~2000 ms
on miss
Store in Redis + TTL
next read is a fast HIT
Key step: on a MISS, write the result back into Redis with a TTL — otherwise every request keeps hitting the DB.
2

Cache Stampede

A hot key expires and thousands of concurrent misses hammer the DB at once.

● No protection
Hot key TTL expires
10,000 requests miss together
10,000 DB queries at once
Database crashes 💥
● Lock / single-flight
Hot key TTL expires
First request acquires lock
others wait ~50 ms
rebuild once
Cache refilled → all read it ⚡
DB got 1 query, not 10,000
Options: lock / single-flight, stale-while-revalidate, jittered TTLs (don't expire together), and pre-warm before a known spike.

Idempotency — Payments

Retries and duplicate webhooks must never double-charge.

● No idempotency key
3 clicks + 2 webhooks
5 requests, one payment
chargeCard() runs 5×
₹25,000 charged 😱
● order_id key + atomic claim
5 requests · same order_id
claim (SET NX)
1st wins
charges once
other 4
return saved result
₹5,000 charged once 💰
Client reuses the same key (order_id) on every retry; server claims it atomically (SET NX / DB unique constraint) so concurrent duplicates can't slip through. Proven: 5 concurrent → 1 charge.
4

Out-of-Order Updates

The network doesn't guarantee delivery order; a late update can overwrite a newer one.

● No versioning
"Delivered" arrives → saved
then, late
"Confirmed" arrives late
overwrites the status
DB shows "Confirmed" — wrong 😱
● Version / timestamp
Each update carries a version
Confirmed(1) Shipped(2) Delivered(3)
"Delivered"(3) → saved
1 > 3 ? no
"Confirmed"(1) late → ignored
stays "Delivered" 🎯
Rule: attach a version or timestamp and apply only if newer than what's stored. A smaller number arriving late is old news — ignore it.
5

Cancellation — State Machine

"Newer wins" isn't enough; some transitions must be illegal.

● Version check alone
Order = "Delivered" (3)
4 > 3 → apply
"Cancelled" (4) applied
Cancelled after delivery 🍕❌
● Allowed-transitions
Delivered → (final)
Cancelled → (final)
legal?
"Cancel a delivered order" → NO
Reject → refund/return flow ✅
flag for a human
Two gates: version (is it newer?) + state machine (is the transition legal?). Illegal ones are rejected and routed to reconciliation — never left to corrupt the status.
6

Lost Updates

A webhook or message is dropped and the update never lands.

● Fire-and-forget
Marketplace → webhook
network drop
Delivery fails silently
Order lost — paid, no record 😱
● Retries · DLQ · reconciliation
Event → queue → worker
on failure
Retry with backoff (3×)
Dead-letter queue
+ alert
Reconcile job
sync vs source
Layered safety: retries + backoff → dead-letter queue (failures aren't lost) → periodic reconciliation that compares your DB against the source and pulls anything missed.
7

Authorization — RBAC + Ownership

A role check alone lets a user reach another user's records (IDOR).

● Role check only
vendorA (role: vendor) ✅
GET /settlements/s2
"Is a vendor?" → yes
s2 belongs to vendorB
Returns vendorB's money 😱 (IDOR)
● RBAC + ownership
authorize("settlement:view-own")
ownership
s2.vendorId === vendorA ?
no
403 — not your settlement 🔒
Two layers: the role decides what actions are allowed; the ownership check restricts you to your own rows. Frontend hides for UX; the backend enforces for real.
8

Zero-Downtime Deployment

Ship new code without dropping a single request.

● Restart everything at once
Deploy
Kill all instances
0 servers
Requests fail 💥 — lost orders
● Rolling + graceful shutdown
Start new instance
health check ✅
Drain one old instance
server.close() — finish in-flight
repeat
Count never drops → 0 dropped ✅
Never all at once. Rolling / blue-green / canary + health checks + graceful shutdown (server.close()) + backward-compatible migrations. Proven with PM2: zero dropped requests.
