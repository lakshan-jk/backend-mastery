🔗 URL Shortener — System Design

Turn a long URL into a short code, and redirect clicks back to the original. Built + tested in ~/backend-mastery/url-shortener/.

read-heavycache-aside Redis INCRcounter + base62

1What it does — 2 operations

SHORTEN (write, rare):
  POST /shorten { url: "https://example.com/bedsheet" }
  → { code: "5", shortUrl: "short.ly/5" }

REDIRECT (read, VERY frequent):
  GET /5  → look up "5" → 302 redirect to https://example.com/bedsheet
🔑 Key fact: it's read-heavy — 1 person creates a link, thousands click it. This shapes the whole design (→ caching).

2Generating the code — 2 options

The code is NOT made from the URL's letters. The URL and code are separate — we just store a pairing (like a coat-check ticket → your coat).

OptionHowLengthCollisions?
Randompick 6 random chars from 0-9,a-z,A-Zfixed 6 (~56B combos)possible → check DB
Counter + base62give each link the next number, encode base62grows (or pad)never ✅
# Counter + base62 — concrete values
counter starts at 0
URL #1  example.com/bedsheet  → counter 1 → base62 "1"  → short.ly/1
URL #2  example.com/pillow    → counter 2 → base62 "2"  → short.ly/2
URL #3  example.com/curtains  → counter 3 → base62 "3"  → short.ly/3
...
URL #1,000,000               → counter 1000000 → base62 "4c92"  # 7 digits → 4 chars
⚙️ base62 = writing a number with 62 symbols (0-9, a-z, A-Z) instead of 10 — like an odometer with 62 per wheel. More symbols → shorter code for big numbers. Want fixed 6 chars? Pad with zeros, or start the counter high.
🔑 Why counter wins: counting up never repeats → no collisions, no DB checks. Random needs a "is it taken?" check every time.

3Scaling reads — cache-aside (Redis)

Every click looking up the DB = the DB doing the same lookup thousands of times. Put Redis in front.

click short.ly/5
   │
   ▼
Check Redis  ──HIT──►  redirect ⚡ (~2ms)
   │
  MISS
   ▼
Look up DB  →  store in Redis + TTL  →  redirect
next click = HIT
BeforeAfter caching
50,000 clicks50,000 DB hits 😰1 DB hit + 49,999 Redis hits ⚡
🔑 Same cache-aside pattern as products — the code→URL mapping barely changes, so it caches perfectly.

4Counting clicks (without hitting the DB)

The tension: if reads are served by Redis, how do we count clicks (which need the DB)? Answer: count in Redis, save to DB later.

on each click:  INCR clicks:5        # +1 in Redis (fast, in-memory)

every 10s (background job):
  read Redis counters → batch-write totals to DB → reset
  # 4,000 clicks = ONE DB write, not 4,000
⚖️ Trade-off: stats are slightly delayed (~10-30s) and a crash could lose a few counts. For click analytics that's fine — speed > perfect accuracy.
🔑 Proven in server-cached.js: clicked 4× → pendingInRedis:4, dbClicks:0 → after flush → dbClicks:4, pendingInRedis:0.

5Full architecture

[ Client ]

    ▼
[ API server(s) ]  ──(behind a load balancer when scaled)
    │
    ├─► [ Redis ]     hot code→URL cache (cache-aside) + click counters (INCR)
    │
    └─► [ Database ]  source of truth: code → URL, click totals
                      (background job flushes Redis counts here every ~10s)
🗣️ Interview delivery: "It's read-heavy, so the core is cache-aside on Redis. Codes come from a counter + base62 so they never collide. Clicks are counted in Redis with INCR and batch-flushed to the DB, trading a little accuracy for speed."
