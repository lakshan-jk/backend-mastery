The two deep-dives from Sunday: how k8s runs/scales/logs your app, and the universal template to draw any system design.

1Kubernetes (k8s)

What is kubectl?

kubectl = the CLI "remote control" for Kubernetes. You type kubectl <command> to inspect or control your cluster.

kubectl get pods              # list pods
kubectl logs <pod>             # one pod's logs
kubectl logs <pod> -f          # -f = follow = live stream (like tail -f)
kubectl logs -l app=order-api  # ALL pods with that label at once

Why multiple pods?

Capacity3 pods ≈ 3× the traffic one can handle
Survive failureone pod dies → others keep serving (no outage)
Zero-downtime deploysupdate one while others serve (rolling)

A "pod" = a running copy of your app. Names get a random suffix: order-api-7d9f, order-api-2k1p…

⚠️ The logging insight (you reasoned this out)

A request only lands in one pod — and you can't predict which (the load balancer spreads them). So kubectl logs pod-1 may not have order 777; it's in some other pod.

order 777 → LB → ??? → any of the 4 pods
you check   →      pod-1        → empty (wrong pod)
🔑 That's WHY centralized logging (ELK) exists: all pods ship logs to one place → you search orderId:777 once, found no matter which pod. Bonus: ELK keeps logs even after a pod restarts (kubectl logs loses them).
Without ELK: kubectl logs -l app=order-api | grep 777 searches all pods at once — but history is lost when pods restart.

🔑 In k8s you don't set up a LB manually — a Service gives it to you. Readiness probes (/health) ensure traffic only hits ready pods → same idea as zero-downtime.

🗣️ Interview one-liner (k8s)

"Each app box runs as pods; a Service load-balances across them (round-robin via kube-proxy), and readiness probes ensure only ready pods get traffic. Ingress handles HTTP routing + SSL. On AWS a type: LoadBalancer Service provisions an ALB. For logs I don't chase pods — all ship to ELK and I search by orderId."

🔑 Memorize this ONE skeleton → customize it for any prompt. Every system = this spine with different emphasis.

The draw-order (so you never freeze)

1. Client(s)          who's using it?
2. Entry point        Load Balancer → API
3. Where's the data?  Database (source of truth)
4. Make reads fast    Cache (Redis) in front of DB
5. Make writes async  Queue + Workers (if heavy/spiky)
6. Side systems       CDN, blob store, observability
7. Annotate hard parts  idempotency, consistency, scaling

3 questions that pick your boxes: Read-heavy or write-heavy? · Real-time (WebSocket) or not? · What can go wrong (duplicates/scale/failures)?

Load Balancer — what / why / which / how

Whatsits in front of app servers, spreads requests, health-checks them, one entry point
Whyneeded the moment you have >1 instance → scaling + high availability + zero-downtime
WhichAWS ALB (L7, routes by path/header) ⭐ · NLB (L4, raw speed) · Nginx/HAProxy (self-host) · k8s Service/Ingress
Howconfigure (not code): algorithm (round-robin / least-conn / ip-hash), health check /health, target group, SSL termination. Keep sessions in Redis so no sticky sessions.
🗣️ "A load balancer spreads traffic across instances, health-checks them, gives one entry point — it's what lets me scale horizontally and deploy zero-downtime. On AWS: an ALB with round-robin, a /health check, SSL termination, and an auto-updating target group. Sessions live in Redis so I don't need sticky sessions."
