① Duplicates

Threat: same order webhook fires 2–3×. Fix: order_id as idempotency key + UNIQUE constraint → processed once.

② Out-of-order updates

Threat: "confirmed" arrives after "delivered". Fix: version/timestamp — apply only if newer; ignore stale.

③ Lost updates

Threat: a message is dropped. Fix: retries + backoff → dead-letter queue → periodic reconciliation.

④ Illegal transitions

Threat: cancel an already-delivered order. Fix: state machine — reject illegal moves → route to refund/return flow.

⑤ Read scale

Threat: status pages hammer the DB. Fix: Redis cache-aside + TTL, invalidate on write; read replicas if needed.

⑥ Spikes / marketplace down

Threat: flash-sale burst, source API flaky. Fix: queue absorbs spikes; workers scale out; retry with backoff.

🗣️ How to present this in the interview

1. Clarify: how many marketplaces, volume, webhook vs poll, latency needs? 2. Shape: "event-driven — ingest, queue, workers, Postgres as source of truth, Redis for reads." 3. Flow: walk left→right as above. 4. Deep-dive: the 6 hard parts (idempotency, versioning, DLQ, state machine). 5. Trade-offs + business: "consistency matters more than instant sync — a wrong order status loses trust; queue + reconciliation guarantees we never lose an order."
